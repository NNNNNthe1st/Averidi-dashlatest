# KPI target information

Original requirement 161: KPI cards contain metric values, previous-period comparisons and target information. Existing target authoring, metric definitions and alert logic are preserved. Target information is an additional, freshly authorized annotation on the existing dashboard-data response.

A target appears on a KPI only when all of the following match: current workspace and dataset, a ready governed metric key and definition version, its currency (or null for non-currency goals), the exact selected inclusive start/through dates and the single confirmed business date field. The query must contain exactly that date filter; category/missing filters, multiple date filters, unfiltered data, another date field, ambiguous time dimensions and a different target period do not receive a dataset-wide goal. Legacy unbound or mismatched-definition/currency targets are omitted. This prevents, for example, a Web-only value from being presented against an all-channel goal.

Cards show up to three matching goal names/values with the full target period and link to the existing monitoring page. A partial-period comparison explicitly distinguishes the current observed-through date from the full goal's through date; the full-period target is never multiplied down or guessed. The original target domain has no saved direction/pacing policy. These annotations therefore do not label a goal ahead/behind/met or assume that higher is better; pace-aware interpretation remains original requirement 143. Currency/percentage/count display uses the metric's existing formatter, and the exact saved decimal value remains in the response and display tooltip.

Annotation admission is bounded to 100 matching records with an explicit `hasMore` flag. Current `monitoring.read` permission is checked before and after fetching annotations. A chart-only custom role receives neither target rows nor existence/truncation information. Existing current membership, entitlement, view sharing/revision and `views.read`/analysis checks remain authoritative before the combined response returns.

Goals are fetched outside the optional signed metric-result cache. Goal edits are visible on the next dashboard data request, even when that request uses a warm metric cache and does not reread source bytes. Goal data is never silently reused from the cached metric payload. Existing CSV calculations and worker reports retain their existing governed behavior; this change adds KPI card annotations rather than changing a report format or target evaluation rule.

Native PostgreSQL tests exercise exact scope and partial observation, category/period/currency/definition refusals, foreign tenancy, a chart-only custom role, the 100-record bound and actual goal edits on a warm cache hit with the source file temporarily unavailable. The production HTTPS browser fixture creates/updates/removes a real scoped goal and checks the KPI card, fresh values, category/unfiltered omission and desktop/mobile accessibility within the unchanged Studio flow. Final whole-branch results are recorded in the architecture progress log.
