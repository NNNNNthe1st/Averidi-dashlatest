# Fictional sample demo and first-use guidance

Original requirements 192 (understand the product before uploading sensitive data) and 190 (guided first use). `/dashboard/app/demo` is an independent read-only public sample page. It accepts no workspace, dataset, credential, upload, source URL or arbitrary filter input. Eight explicitly fictional `DEMO-` orders are compiled into this product; no demo tenant, subscription, session, database record or external provider is created. The page uses the existing governed analysis/template/widget engines, not hand-entered displayed KPI totals.

The sample has fixed USD, UTC, one-order-per-row and explicit revenue/cost/return/cancellation assumptions. It demonstrates KPI results, formulas and input lineage, category filtering, time/channel breakdowns and February/January calendar comparisons. January has no invented earlier comparison. The complete fictional source and confirmed sample rules are visible. The sample CSV is exactly generated from those same records; its checked-in copy is checked by the unit suite. This is sample data, not a report of a real customer's business or an assumed configuration for new customer datasets.

Only the fixed All/Web/Shop/Partner and January/February selections are accepted. Unknown, duplicate or unsupported selections display a fixed reset message and return the default fictional view. There is no raw URL/text reflection. Channel and period controls submit GET requests back to the sample page; the demo never calls customer APIs. The download is a static fictional CSV, not an authorized customer artifact endpoint. Editing, connector management, billing, invitations and persistence remain in the existing account/workspace workflows.

The proxy explicitly permits GET/HEAD on this synthetic page even when customer release is OFF; customer pages and APIs retain their release and authorization gates. This is a development source change, not a production deployment. The existing workspace chooser links to the sample, and the sample links to the existing sign-in/workspace entry. The application's no-index metadata remains in place. English remains the interface language.

The existing saved-state six-step Studio guide retains its progress logic. An additional expandable explanation covers period/definition-bound targets and threshold alerts, the distinction between source processing and calculation timestamps, lack of inferred external-source completeness, and the upload/append/synchronize/connector-update → job → confirmation → calculation → dashboard sequence. It explains that the dashboard refresh control consumes current ready calculations rather than performing a provider fetch, and preserves explicit Save behavior. Monitoring/data links respect the current custom read permissions. It also links to the fictional demo.

`tests/demo.test.ts` checks exact native calculation/filter/comparison results, deterministic valid widget definitions, immutable fictional records, unsupported-input refusal, CSV identity and the isolated public-route exception while protected routes remain closed. The anonymous HTTPS browser fixture exercises controls, formulas, download, no customer API requests/cookies/record creation, invalid selection recovery, desktop/mobile accessibility and overflow. The existing Studio browser workflow expands the new guide and validates it alongside the unchanged upload-to-dashboard flow. Full results are recorded in the architecture progress document for this batch.

The source-freeze verifier includes public assets as well as runtime code. Its regression distinguishes public CSV changes and untracked public additions from narrative-only documentation updates, so the sample download cannot silently differ from the verified source identity.
