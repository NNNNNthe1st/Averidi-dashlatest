# Dashboard mutation evidence and activity history

Audit 210. Existing domain, administrative and organization audit records remain in use. A separate `DashboardMutationAudit` journal adds automatic, transactional evidence for all 63 original persistent Dashboard resource models (and the subsequently added account-erasure queue). Worker heartbeat and request-rate counter tables are deliberately excluded; the journal does not recursively journal itself. No history is invented or backfilled for mutations that predate this migration.

Each committed insert, meaningful update and delete records the resource class and opaque ID, workspace/organization/user scope where applicable, operation, changed column **names**, transaction ID, timestamp in UTC and actor provenance. No source rows, profile names, support messages, definition/configuration values, billing amounts, credential ciphertext, OAuth codes, cookie/JWT values or webhook bodies are copied into this journal. Timestamp-only changes, heartbeat/lease renewal fields and job progress alone are excluded to avoid logging liveness as resource changes.

Existing transactional services bind their verified actor using transaction-local context; formerly single-statement profile, membership-administration, view, session and queue writes use the same bounded transaction boundary. Worker publication binds the actual job ID. Actor context clears when the transaction finishes and cannot leak through pooled connections. Existing domain-event rows contribute their explicit actor and action, and share the transaction ID with the corresponding resource evidence. A provider/domain actor that differs from the calling customer is not mislabeled with that customer's user ID. Unattributed internal/database writes are clearly labeled `DATABASE_ROLE` with the database role, never invented customer identity. Request body actor fields cannot establish this server context. This context is attribution from trusted application code, not an alternative authentication mechanism.

Mutation and journal insertion commit or roll back together. Journal insertion failure fails the resource mutation. Runtime UPDATE/DELETE attempts against past journal rows are rejected by PostgreSQL, except the strictly scoped identifier-only privacy redaction described below; the runtime role has no TRUNCATE or schema-owner privilege. Journal records have no cascading resource foreign keys, so deleting a workspace, membership or user cannot silently remove its mutation evidence. This is operational append-only evidence, not a claim of cryptographic immutability against the database owner. Retention and later authorized privacy redaction require an explicit governed policy; no retention period or automatic deletion policy is invented here. The account-erasure extension permits an active RUNNING request to clear only its own user/actor references and replace its verified identity aliases with an opaque erasure reference. PostgreSQL compares every other column with the original row; operations, timestamps, transaction IDs and resource evidence cannot change, and DELETE remains rejected. See [account-erasure.md](account-erasure.md) for the explicit privacy and shared-record boundaries.

## Authorized reads

- Workspace Owners: `GET /dashboard/app/api/workspaces/<workspaceId>/activity`, and **Workspace activity** in Owner navigation. Membership is checked even after subscription expiry. Editors/Viewers and custom profiles cannot gain Owner access through a URL or alternate parameter.
- Current account: `GET /dashboard/app/api/account/activity` and **Account activity** from account settings. Only that actor's non-workspace/non-organization account records and actions are returned. This is not a way to inspect another person's account or a workspace's business history.
- Independent administrators: `GET /dashboard/app/api/admin/v1/mutations`, requiring the existing independently verified `dashboard:read` capability. Optional `workspaceId` filters the administrative result. Existing `/admin/v1/audit` behavior and records are preserved.

All reads are private/no-store. Default page size is 50, maximum 100. Filters are `resourceType`, `operation` (`INSERT`, `UPDATE`, `DELETE`) and `transactionId`, with strict duplicate/shape checks. Pagination orders by timestamp and ID; a cursor must be visible within the same scope and filters. Browser screens render 25 events at a time with older/newer navigation and accessible scroll regions rather than accumulating an unbounded table. IDs and column names are evidence metadata, not bearer authorization. Cross-tenant and foreign-cursor requests are rejected.

## Migration and verification

Apply the migration and the established runtime grants before starting the upgraded application/worker (`npm run db:deploy`, `npm run db:grant`). The table is Dashboard-owned; no external database, website source, Analyst module, provider or integration is used. There are no new dependencies or job kinds. Application calculations and billing financial treatments are unchanged.

`npm run test:mutation-audit` checks actual PostgreSQL trigger coverage, trusted actor/pool isolation, private-value exclusion, rollback, edit/delete rejection, worker/domain correlation, account/tenant/role/cursor limits, session rotation and resource-deletion retention. `npm run verify:mutation-audit` adds a clean typecheck/build, actual HTTPS activity screens and pagination, desktop/mobile accessibility, all existing source/OAuth/BI/customer workflows and separate HTTPS OIDC acceptance. It requires the same disposable loopback test database and separate runtime/migration roles as the existing verification commands, and refuses other databases before fixture writes.


## Anonymous operational observations

`DashboardObservationBucket` is excluded from mutation evidence alongside existing heartbeat/request counters. It stores only bounded controlled route/job labels, minute windows, outcome counts and elapsed durations; it contains no tenant/user/source identity or source values and is pruned after 24 hours. Auditing every counter increment would recursively amplify operational traffic. `DashboardSourceMonitoringPolicy` and `DashboardSourceIncident` remain business state and have atomic mutation-evidence triggers.
