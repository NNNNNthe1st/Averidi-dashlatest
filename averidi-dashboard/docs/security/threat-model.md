Review date: 2026-10-25. Original requirement 338: uploads, APIs, connectors, sharing, exports and admin paths reviewed. Baseline: branch `feature/independent-dashboard`, published cache commit `7612cccfe8ff9142afd17cfb605ad20e1cf7fcdd`, plus the scoped administrative diagnostics change recorded in the architecture progress log. Reviewer: coding assistant, by source inspection and related local acceptance evidence. This is a completed development threat-model review, with an open risk register; it is not independent penetration-test certification, human risk acceptance or production approval.

## Assets, actors and trust boundaries

Protected assets are uploaded source rows, analysis and financial values, mappings/rules/formulas, workspace/team membership and sharing capabilities, customer/session identities, connector credentials, billing receipts, stored artifacts/backups and audit/erasure evidence. Ordinary users, another tenant's members, an authenticated viewer, a malicious workspace editor, untrusted file/provider content, network attackers and forged/replayed webhook/token senders are considered adversarial. An authorized administrator can legitimately inspect multiple tenants' metadata; compromised administrators, deployment credentials, database owners and hosts remain high-impact trust assumptions rather than actors the application can fully contain.

The boundaries are: (1) public HTTPS to application/proxy, (2) signed identity to server-owned actor/session, (3) actor to currently authorized workspace/custom permission/subscription/view, (4) application/worker to dedicated runtime database/private storage, (5) worker/connector to untrusted provider networks, (6) provider webhook to signed tenant-bound receipt, (7) operator JWT to independent admin API, and (8) local persistence to backup/restore/erasure workflows. Website and Analyst source/runtime/database are outside this product boundary; their integration flags remain inactive. Database-name checks are configuration guards, not proof of physical separation.

## Open risk register and acceptance ownership

| ID | Risk / required evidence | Existing mitigation | Required next acceptance |
|---|---|---|---|
| R1 | Malicious multipart/XLSX inputs can create parser CPU/memory pressure before all normalized dataset limits apply; worst-case resource acceptance is absent. This is an identified assurance gap, not a demonstrated exploit in these tests. | File limits, normalized row/column limits, supported parser, authorization and request budgets. | Development/security: bound the full upload-read/parser resource path and run hostile compressed/malformed workbook pressure cases; operations: verify actual ingress/body/time/process-memory limits. Do not treat ordinary workbook tests as that evidence. |
| R2 | Stolen valid operator/session credentials and an overprivileged identity issuer permit legitimate-looking access. | Signed short-lived tokens, separate admin audience/permissions, secure sessions/revocation and attributable audit. | Product/security/operator: approve issuer/operator access policy, verify MFA/account lifecycle and incident/revocation behavior in the actual environment. No policy or sign-off is invented here. |
| R3 | Misconfigured or compromised deployment secrets, runtime database/storage permissions, ingress and backups can bypass application assumptions. | Dedicated-variable guards, restricted-role verification, private storage, encryption context, maintenance fences and local real recovery. | Operations: verify physically separate resources, key custody/rotation, private network/transport/backup access and off-host recovery. Existing production-pending roadmap items remain pending. |
| R4 | Live provider contracts/permissions and changes may differ from fixture assumptions. | Fixed validated adapters, bound credentials, refusal/limits and source-specific fixture/browser coverage. | Provider acceptance per connector and approved activation; no live connection is activated by this review. |
| R5 | Authorized recipients retain exported/downloaded data after membership revocation or erasure. | Authorization at retrieval, restricted source linkage and explicit internal erasure boundaries. | Product/legal: approved customer disclosures and downstream handling terms. Do not promise recall of external copies. |
| R6 | Compromised hosts/database owners can read data and keys or change source/evidence; local controls alone are insufficient. | Least-privilege runtime distinction, authenticated encryption/signatures, append-only runtime evidence and tested restore/erasure controls. | Operations/security: controlled privileged access, off-host evidence/backup custody and live monitoring/on-call acceptance. |
| R7 | Dependency vulnerabilities or untested parser/browser behavior may remain despite successful regression tests. | Lockfile, independent source boundary and reproducible local gates. | Recurring vulnerability triage and successful hosted dependency-security runs remain requirement 342; manual/device acceptance remains separately pending. |

No risk is silently accepted as a business decision. Open controls retain their own implementation/live-acceptance status. Requirement 338 records the documented review of all named surfaces; it does not mark R1–R7 or the whole product complete. Any future PDF/image renderer, public API credential service, outbound delivery, new provider or cross-product activation must update this model and its adversarial tests before release.
