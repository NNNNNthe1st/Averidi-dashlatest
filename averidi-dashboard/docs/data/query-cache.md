# Dashboard query-result caching

Original requirement 222. This optional independent PostgreSQL cache avoids preparing source bytes and recalculating widgets for repeated identical dashboard/filter queries. The normal calculation remains authoritative on every miss or cache failure. No cross-product runtime, database or cache service is introduced.

Enable `DASHBOARD_QUERY_CACHE_ENABLED=true` only with `DASHBOARD_WORKER_ENABLED=true` and a dedicated random 32-byte hexadecimal `DASHBOARD_QUERY_CACHE_KEY`. Do not reuse an authentication, billing, connector or erasure key. The example configuration leaves the cache off. Invalid enabled configuration makes readiness fail and prevents worker startup; dashboard calculations can still use the uncached path. Readiness requires a live worker advertising `QUERY_CACHE` when enabled.

Entries bind to workspace, view revision/definition, engine, current ready analysis, dataset version, checksum, confirmed semantic revision/rules and validated filter/comparison query. Both initial and final checks enforce current membership, custom `views.read` permission, subscription, view sharing and active analysis. A changed view revision refuses the response. The cache does not grant access and never supplies ungoverned results. Source bytes are integrity-checked on the cold path; a warm entry represents those verified immutable bytes, rather than a new physical-file integrity scan on each request.

Exact serialized result bytes and scope/timestamps carry an HMAC using the dedicated key. A tampered record, invalid signature, expired entry or key rotation causes a miss. The response hydrates the analysis timestamp back into a Date. Cache contents include calculated business values and belong within the existing private database, access, backup and erasure boundaries. Mutation evidence records changed field names, never payload values.

Defaults are 300 seconds and 32 entries per workspace; supported bounds are 30–3600 seconds and 1–64 entries. Individual entries cannot exceed 256 KiB. Database constraints enforce bounds on each entry. Per-workspace admission serializes writes; a full cache skips a novel query instead of evicting fresh entries. Writes remove expired/old-policy entries and obsolete scope records for that view. Lowering the configured entry cap blocks new admission until existing entries expire; it does not synchronously delete fresh records. This is a configured technical cache lifetime, not a customer data-retention policy.

The native worker removes up to 500 expired records at startup and every 30 seconds. Cache writes and cleanup respect storage restore maintenance; database erasure-admission triggers and cascading tenant/view foreign keys remain attached. Cleanup skips workspaces fenced for erasure. Cleanup failures remove the cache capability from subsequent worker heartbeats until maintenance succeeds again. Disabling the feature stops reads/writes and maintenance; residual entries remain private and unusable until it is re-enabled or the workspace/view is erased. To purge while disabling, keep the worker enabled through expiry/cleanup first. Dedicated key rotation invalidates previous signatures without changing business definitions.

Acceptance coverage is in `tests/query-cache.test.ts`: real source-file isolation proves the warm path avoids source reads; different filters still require a miss; native PostgreSQL enforces bounds and cascades; tampering/key rotation use verified fallback; revoked sharing, foreign tenancy, inactive subscriptions and changed confirmation cannot use cached values; a real worker cleans expiry and advertises its capability. The complete verification gate additionally checks migration upgrade, restrictive runtime role, all-table recovery, regression, build and existing browser workflows.
