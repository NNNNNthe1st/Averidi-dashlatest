# Visible source quality status

Original requirement 80: customers can see Pass, Warning or Fail. The new source-quality assessment is an informational presentation of validated profile facts and current governed checks. It does not replace calculation eligibility, change metric formulas, treat warnings as errors, or weaken existing refusals. Existing engines and stored analysis results remain compatible; no engine-version change or data reprocessing is required.

| Display | Detected facts |
|---|---|
| Pass | A ready, internally consistent source profile has no detected missing-cell warnings, retained duplicates or applicable governed failure. |
| Warning | At least one field contains missing cells, with no detected failure. Missing cells may be intentional; each metric retains its existing requirements. |
| Fail | Source processing failed, exact duplicate rows were retained, the current analysis is blocked, or a current version/revision/checksum-bound validation failed. |
| Not checked | No ready, internally consistent profile is available. Pending, missing or malformed metadata never becomes a passing result by default. |

The assessment carries its version ID, profile/governed scope, normalized profiled row count, bounded missing-cell field/count warnings and fixed failure codes/counts. It checks profile field/column counts and present-plus-missing totals before presenting a pass. It never returns raw cells, `topValues`, sample records or arbitrary source exception strings. Full field/count details require current `datasets.read`; the analysis/dashboard paths otherwise redact detail. The existing core custom-role policy normally grants dataset/analysis/view read together; this additional projection guard does not change those prerequisites.

Customers see the shared summary before/after calculation in Studio, on an authorized dashboard, and in Data quality review. Source-processing failure can be reviewed even before a first active version exists; validation controls stay disabled until there is a current version. Acknowledging a finding does not clear the source failure. A corrected version can show Pass while prior failed checks remain visible as historical evidence. Stale checks do not poison the current source assessment. All three surfaces use the same server lookup for current version/revision/checksum-bound failures, including findings outside the latest 20 review-history rows; profile-only validation is not mislabeled as governed business validation.

Warnings refer to the complete normalized profiled source, including fields that are not used by a particular metric or current filter. The UI makes that basis explicit and states that Pass does not prove an external source supplied every expected record. Governed calculation checks keep their own displayed status and detailed refusal reasons. A missing optional grouping cell can therefore produce a source Warning while valid revenue remains available. No business-data completeness or freshness policy is invented.

Assessment projection uses metadata already loaded with the selected current version; the quality-review path fetches only the selected active profile and falls back to latest-version status for first-processing failure. The workspace dataset listing is unchanged and does not fetch every source's potentially large profile. Dashboard assessment is assembled outside the signed metric cache from current version metadata, followed by the existing final access/current-state checks; cached arithmetic is not repurposed into an old quality-status snapshot.

Four focused tests cover real profiles, redaction, foreign tenancy, native before/after-analysis/dashboard/review agreement, unchanged numeric results and blocked-analysis refusal, first-processing failure, current validation and stale-check exclusion. Existing data-model and quality-review tests remain authoritative. Native HTTPS fixtures assert Pass, actual missing-category Warning with preserved revenue, duplicate-source Fail and corrected-source Pass, alongside existing desktop/mobile accessibility and workflows. Whole-branch verification is recorded with this batch in the progress log.
